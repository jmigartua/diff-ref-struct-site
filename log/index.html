Control files end .drc; the four faults of the .pcr export fixed; a refinement that can be stopped and each phase's curve

Core 0.17.0. Josu accepted the control file's syntax, the TOML subset of L066, with the extension .drc. The content stays valid TOML. drs convert, drs check, drs calc, drs refine, drs data info, the tests, the README and manuals/fullprof/runs/export_runs.py now use .drc.

The four faults of the .pcr export found with FullProf in L069, fixed:

  • the resolution file's name is alone on its line, after a comment line, as in FullProf's own files;
  • Thmin, Step and Thmax are written as the .pcr gave them (Co-YBCO's Thmax 150.0, Egypt's step 0.010002);
  • the excluded regions come out as they went in (Co-YBCO 0–5; Egypt 5.00–6.70 and 75–180);
  • VARY lines come straight after the wavelength line, as in FullProf's files (LaB6's VARY ratio).

How the range and the regions are kept. The import turns FullProf's regions into the data points FullProf leaves out (Co-YBCO's 0–5 becomes 0.069–5.019; the rule of L033 leaves out a point whose step reaches into a region). That loses the numbers that were written, and no arithmetic brings them back: widening 0.069–5.019 by half a step gives 0.044–5.044, and under the rule of L033 that would leave out one more point at each end.

So the control file keeps what the .pcr wrote in a table of its own, [pattern.fullprof]: range (Thmin, Step, Thmax) and excluded_regions. The export writes them back while the model's regions still leave out the same points.

Regions changed or added after the import are written half a step inside their first and last points, as the rule needs, and a step beyond the data at its ends, never clamped to the data. The export says so in a note. The range is the data's when the data are written processed.

Test control_file checks, on all 62 runs, the exported .pcr against the original, numbers compared as numbers:

  • the resolution line is one field, the file written;
  • Thmin, Step and Thmax are equal;
  • the excluded regions are equal;
  • VARY ratio is kept where the original had it, and every VARY/FIX line comes straight after the wavelength line.

The export now goes through the control file's text, as drs convert does. FullProf cannot run in the cloud: the exported files are for Josu to run again with export_runs.py on the Mac. The export is not claimed until FullProf reproduces every run it accepts (L069).

Stopped, the refinement returns the model at that cycle's values, with esd's and correlations, and stop = "stopped by the user" (lsq::STOPPED). refine is unchanged for its callers. In drs refine, Ctrl-C stops after the cycle in progress and prints the results (a Le Bail run of MgAl2O4 stopped at cycle 376 of 500).

Our own control file (a strict subset of TOML, for Josu to accept) and the data operations of the Data module

Core 0.16.0. Josu accepted L062's points: the five frozen \(\sigma\) sums and the question of the point at an excluded region's end, Ins 9 and Ins 14 read as believed, and the GSAS reader following the BANK record's NCHAN.

The control file (P47, Q3), for Josu to accept. The syntax is a strict subset of TOML 1.0, files ending .toml. Reasons, against the requirements:

  • readable and diffable: one key = value per line, a table per part of the model ([pattern], [pattern.background], [[phase]], [[phase.atom]], [[restraint]], [refine], [convention]), no indentation that carries meaning, so a diff shows the value that changed and nothing else;
  • typed values without guessing: strings are quoted, numbers are numbers, true/false are booleans;
  • comments with #, kept with the user's order and formatting when the file is written again after a change;
  • every file is valid TOML, so other tools read it (Python's tomllib read the 8 runs converted by the command line); our parser is our own (no dependency) so that it can keep the comments and give each key and value its line, column and span.

Left out of the subset, each reported where it occurs: dotted keys in key/value lines, multi-line strings and dates. This leaves one way to write each thing.

Set aside:

  • YAML: indentation carries meaning; implicit typing ("no" read as a boolean, version strings read as numbers); a large specification; keeping comments on rewrite needs a heavy library;
  • JSON: no comments and noisy to read by hand. It stays the app's interchange format for the model (L058);
  • a syntax of our own in the manner of CrysFML's CFL: readable, but no other tool reads it, and every rule would be ours to document;
  • the .pcr itself: positional columns that are not named.

The file holds:

  • a format line format = "diff-ref-struct 1";
  • the pattern: the data file by its path relative to the control file, the registry's reader id, wavelengths, instrument, corrections, excluded regions, background, resolution, and the data operations;
  • phases (space group as H-M and Hall symbols, cell, profile, preferred orientation, Le Bail flag) and atoms;
  • restraints;
  • the refinement: each parameter written as its terms, the first naming it; equalities with their multipliers; limits; linear restraints; cycles and convergence. The symmetry's ties are implied, not repeated;
  • the ten convention switches.

Keys are the parameter dictionary's ids (sample_displacement, not Sycos), with the dictionary's unit as a trailing comment; choices are words (debye-scherrer, thompson-cox-hastings, maximum-likelihood). Floats are written in the shortest form that reads back to the same bits. Unknown keys get a suggestion by edit distance ("did you mean zero_shift?").

Results (test control_file):

  • all 62 runs the core imports (the runs of manuals/fullprof/runs and the window experiments) were written, read back and written again: model identical to the bit, the same pattern and \(\chi^2\) (to the bit), the same parameter set as ParameterSet::from_pcr, the data file found again, the text identical. The three runs the import itself refuses (NdNi-LTOa, NdNi-LTOb, Pd3MnD: anisotropic size and strain, version 2) are not among them;
  • a file edited by hand (comments, moved keys, values in their own notation), updated after a change, keeps everything but the changed value;
  • 8 kinds of mistake are reported at their line and column. drs check prints them as file:line:column:, in the text's order, and the outline lists each table's lines for folding (app request 11).

The export to .pcr inverts the import's translations exactly: the scale halved, P1 − 3P2 and P3 − 3P4, the axial pair, the sign of the exponential G1, and the excluded regions narrowed by half a step. Codewords are C = sign(a)(10p + |a|). The .irf and the CODFILn.hkl of profile-matching phases are written next to the .pcr; processed data are written as .xys (Ins = 10).

All 62 runs were exported and imported again by the core's reader: identical models, zero pattern and \(\chi^2\) differences, and the same parameter sets. FullProf itself was not run (cloud).

What FullProf cannot express is listed as a note:

  • a value that moves with two parameters;
  • multipliers of 10 or more;
  • the user's limits;
  • the default model's taper of the peak window;
  • the reflection range;
  • the angle restraints' weight (3 runs);
  • processed data, or a reader with no Ins;
  • the Chebyshev range;
  • the λ2/λ1 ratio refined, written as FullProf's VARY ratio command (2 runs).

drs convert goes both ways; drs calc and drs refine read control files.

The data operations (R21; app request 10). Module data_ops: an ordered list of operations, written in the control file as [[pattern.operation]] tables. drs::control::open applies them to the scan read from the file; the file is never changed. The operations:

  • mask (\(\sigma\) = ∞) and delete, by range or by points;
  • Savitzky–Golay smoothing (SciPy's mode = "interp" at the ends), \(\sigma\) propagated;
  • rebinning by a factor or to a new step, summed (counts conserved) or averaged;
  • normalising to a monitor, a counting time, a maximum, or by a factor;
  • adding and subtracting another file's scan (linear interpolation, \(\sigma\) propagated), and merging (1/\(\sigma\)² weights);
  • conversion between 2\(\theta\), d and Q, and to another wavelength.

The analyses:

  • peak search: SciPy's prominence and width at half prominence;
  • GSAS-II's peak candidates;
  • the automatic background: arPLS with GSAS-II's λ and 10 iterations.

Test data_operations, on four real files (GSAS-II's AutoBkg tutorial scan, PbSO4 X-ray, garnet neutron data, Y2O3 of FullProf):

  • 669 smoothed points and their \(\sigma\) against SciPy (to 1e-9);
  • 348 peaks: indices exactly, prominences and widths against SciPy's find_peaks and peak_widths;
  • 538 peak candidates, the same indices as GSAS-II's own lines of OnAutoSearch;
  • 262 background points within 8.3·\(10^{-10}\) of the largest count of pybaselines' arPLS, as GSAS-II calls it, with the same number of iterations;
  • 205 rebinned sums against numpy.

Exact identities: d·Q = 2π; 2\(\theta\) → d \(\to 2\)\(\theta\) and 2\(\theta\) → Q \(\to 2\)\(\theta\); a change of wavelength keeps d; normalising scales y and \(\sigma\) alike; a scan added to itself gives \(\sigma\)√2, and merged with itself gives \(\sigma\)/√2; interpolated \(\sigma\); counts conserved by rebinning. GSAS-II's STD-bank count (NCHAN − 1, L062) is followed for PbSO4's references. drs data op | apply | peaks | background | info; info also names the other files of a project (formats::project: .pcr, .out, .sum, .prf, .hkl, .sym, .mic, .irf, CIF; app request 9).

App requests: 8 and 9 were closed by 0.15.0 (info completes 9); 10 and 11 are closed by this release.

For Josu:

  • the syntax and the .toml extension;

Q1: the core in Rust, with Python as its scripting interface

Josu decides design question Q1. The core is written in Rust; Python is the interface for scripting, through bindings to the Rust core (PyO3), in version 2 as the proposal has it (P48). No physics is written in Python. The reasons, from the comparison made in the conversation:

  • Tauri's side is Rust, so the core links straight into the Mac app: one signed binary, no interpreter or local server to ship and start (the difes-shell way, which works but is heavier).
  • The same crate builds the command-line program that every feature needs (CLAUDE.md), and its tests run with cargo test in a cloud session as well as on the Mac.
  • Most of the code is written by Claude sessions; Rust's compiler rejects whole classes of errors (types, memory, data races) before any test runs.
